# PlayGround

A playground for Google Workspace/Drive APIs, PDF structural parsing, JIRA automation and
LLM image comparison. Four independent tools live here: the Directory/Drive web app (§1), the
BC Building Code PDF/web indexes and viewer (§2–4), the AOT Pulse JIRA backlog creator (§5)
and the LLM image comparison (§6).

## 1. Directory/Drive web app (`app.py`)

A FastAPI app with "Sign in with Google" (OAuth2). Once logged in, a user can:

- List all names/emails in the `aot-technologies.com` Workspace directory (via the People
  API, falling back to the Admin SDK Directory API for admin accounts).
- List the subfolders of a fixed Google Drive folder.
- Cross-check directory users against Drive folder names by fuzzy name match (word-by-word
  similarity, not raw character-sequence matching — naive whole-string matching produced
  false positives on short names), surfacing:
  - users with no matching folder, and
  - folders with no matching active user.

### Setup

Needs a **Web application**-type OAuth 2.0 client in Google Cloud Console, with:
- APIs enabled: People API, Admin SDK API, Google Drive API
- Authorized redirect URI: `http://localhost:8000/auth/callback`
- Downloaded as `credentials.json` in the project root

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

### Run

```bash
export SESSION_SECRET=$(python -c "import secrets; print(secrets.token_hex(32))")
python -m uvicorn app:app --reload
```

Then open `http://localhost:8000` (use `localhost`, not `127.0.0.1` — the two are treated
as different origins by the session cookie, and the login flow will fail if you mix them).

### Directory-access CLI check (`src/check_directory_access.py`)

A standalone script that checks, outside the web app, whether a given Google account can
list the Workspace directory via the People API vs. the Admin SDK, and prints which path
works and why.

Needs a **Desktop app**-type OAuth 2.0 client (separate `credentials.json` from the web
app's — desktop and web clients aren't interchangeable).

```bash
python src/check_directory_access.py
```

## 2. MO Package TOC + Image viewer (`src/mo_toc/`)

Parses `MO Package BCBC MRK signed.pdf` (a 1685-page merged BC Building Code + Ministerial
Order package whose own PDF bookmarks are too coarse to use directly) into a full
hierarchical index — every node carries a page number and a precise bounding box:

```
Volume → Division → Part → Section → Subsection → Article → Sentence → Clause → Subclause
                       └── Notes to Part → Note
Volume → FrontMatter / Appendix chain / BackMatter
```

plus a flat Table/Figure caption index and a full embedded-image index, with each image
matched to the deepest document node it belongs to and, where a nearby caption exists, to
that caption's own Table/Figure identifier.

### Setup

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

Requires `MO Package BCBC MRK signed.pdf` in `data/`.

### Build the index (JSON/Markdown/images)

```bash
# defaults to data/MO Package BCBC MRK signed.pdf
python src/build_mo_toc.py

# or index a different PDF
python src/build_mo_toc.py /path/to/other.pdf
```

Writes `output/bcbc_pdf.json` (full-fidelity index), `output/mo_toc.md` (human-readable index
with page numbers), and `output/images/` (the full-resolution raster image, or a rendered
crop for a vector-drawn figure, for every image the PDF pipeline finds). Safe to
delete and rebuild — everything in `output/` is regenerated by re-running this script.

### Run the interactive viewer

```bash
python src/serve_mo_toc.py
```

Then open `http://localhost:8000`. The viewer renders the PDF page-by-page (pdf.js) with
three sidebar tabs — Table of Contents, Images, and Table of Images (images grouped by the
document node they belong to) — and clicking any entry scrolls to and highlights its exact
bounding box on the page. Builds the index on first run if `output/bcbc_pdf.json` doesn't
exist yet, so `python src/build_mo_toc.py` above is optional but faster to run explicitly
first.

### Tests

```bash
pytest -q
```

Runs the full suite for `src/mo_toc/`, `src/build_mo_toc.py`, `src/serve_mo_toc.py`,
`src/web_toc/`, `src/build_web_toc.py`, `src/shared/`, `src/jira_backlog/` and the other
`build_*.py` scripts (1081 tests). Excludes the
`slow` marker by default (a real-1685-page-PDF integration test and a real-website
integration test); run it explicitly with:

```bash
pytest -q -m slow
```

### Definition of done (for changes under `src/mo_toc/`, `src/build_mo_toc.py`, `src/serve_mo_toc.py`, `src/web_toc/`, `src/build_web_toc.py`, `src/shared/`, `tests/`)

```bash
ruff check --fix src/mo_toc src/build_mo_toc.py src/serve_mo_toc.py src/web_toc src/build_web_toc.py src/shared tests
ruff format src/mo_toc src/build_mo_toc.py src/serve_mo_toc.py src/web_toc src/build_web_toc.py src/shared tests
radon cc -s -n B src/mo_toc src/build_mo_toc.py src/serve_mo_toc.py src/web_toc src/build_web_toc.py src/shared tests
vulture src/mo_toc src/build_mo_toc.py src/serve_mo_toc.py src/web_toc src/build_web_toc.py src/shared tests
pytest --cov=src/mo_toc --cov=src.build_mo_toc --cov=src.serve_mo_toc --cov=src/web_toc --cov=src.build_web_toc --cov=src/shared
```

`Archive DO NOT Refer/` are legacy/archived and intentionally exempt.

## 3. BC Building Code (Web) — Table of Images (`src/web_toc/`)

Builds a second, independent hierarchical Table of Images — this one sourced from the live
[BC Building Code website](https://dev.buildingcode.gov.bc.ca/?version=2024&date=2024-03-08)
rather than the local PDF, using its own `navigation-tree.json` and per-section content JSON.
Served as a fourth tab in the same viewer (`src/serve_mo_toc.py`); each embedded image is
also downloaded once and cached under `output/web_images/`, served locally from there
(falling back to hotlinking the live site for any image that wasn't cached, e.g. an older
`bcbc_web.json` built before this or one where the download failed).

### Build the index

```bash
python src/build_web_toc.py

# or a different site version
python src/build_web_toc.py --base-url https://dev.buildingcode.gov.bc.ca --version 2024
```

Writes `output/bcbc_web.json` and `output/web_images/` (one cached `.jpg` per embedded image,
named after its id). Makes several hundred real HTTP requests to the live site (one per page,
plus one per image) and takes a few minutes; safe to delete and rebuild. Requires no local
PDF or credentials.

Then run `python src/serve_mo_toc.py` as usual — the "BC Code (Web)" tab reads this file if
present, and shows a "not built yet" message otherwise.

## 4. Unified document-level numbering

Both `bcbc_pdf.json` and `bcbc_web.json` trees carry a `unified_number` on every node — a
purely positional `volume.division.part.section.subsection.article.sentence.clause.subclause`
label, computed independently within each tree (1-based position among same-type
siblings under the same parent). Node types outside those nine levels (front matter,
appendices, notes, index/conversion pages, etc.) still get a number, using a short type
marker plus their own position (e.g. `1.2.App1`). Because the PDF and website trees are
shaped slightly differently (the website splits Part 9 - Housing into a second volume,
the PDF does not), the same real section is not guaranteed to carry the same
`unified_number` in both tabs — it's a per-tree outline number, not a cross-reference
key. Shown in the viewer next to each tree row.

## 5. AOT Pulse JIRA backlog (`src/create_jira_backlog.py`)

Creates the AOT Pulse epics, with their stories under them, in JIRA project `AUBM`. It uses
the JIRA Cloud REST v3 calls from `JIRA.postman_collection.json`: list projects, list
assignable users, and create issue. It logs in with your Atlassian account email and an
API token.

### Sources

Both sources live in `AOTPulse Specs/`. Git ignores that folder, so copy it into the
project root yourself.

- **`AOT BidHub — Epics & User Stories.md`:** each `## Epic N` becomes an Epic, and each
  row of its table becomes a Story. A story carries its user story, acceptance criteria,
  FR references and status.
- **`<feature>/spec.md` (spec-kit):**
  - Each epic's description includes the spec it formalizes. Epics 1–9 map to the user
    stories of `001-aot-bidhub`, and Epics 10–15 to `013`–`018`.
  - The `002`–`012` list/detail enhancements aren't in the epics document. Their user
    stories become stories of the module's epic, with their P1–P5 priority mapped to a
    JIRA priority.

That makes 105 issues in all: 15 epics and 90 stories. The epic-to-spec mapping lives in
`src/jira_backlog/domain/aot_pulse_links.py`.

### Configuration

Copy the template and fill it in. Git ignores `jira_config.toml`, so your token isn't
committed.

```bash
cp jira_config.example.toml jira_config.toml
```

```toml
[jira]
url = "https://aottech.atlassian.net"
username = "you@aot-technologies.com"   # your Atlassian account email
api_token = "..."                       # https://id.atlassian.com/manage-profile/security/api-tokens
project_key = "AUBM"
```

Environment variables override the file. Exporting `JIRA_API_TOKEN` alone keeps the token
out of files entirely.

```bash
export JIRA_URL="https://aottech.atlassian.net"
export JIRA_USERNAME="you@aot-technologies.com"
export JIRA_API_TOKEN="..."
export JIRA_PROJECT_KEY="AUBM"   # optional, defaults to AUBM
```

The `[issues]` section is optional:

- `labels`: added to every issue.
- `assignee_account_id`: assigns every issue to one person; `--check` lists the account ids.
- `[issues.priorities]`: maps spec priorities to JIRA priority names.
- `epic_name_field` / `epic_link_field`: only for older company-managed projects that
  still require the legacy Epic Name and Epic Link fields.

Pass `--config <path>` to read a config file from somewhere else.

### Run

Check access to the project and list the account ids you can assign to:

```bash
python src/create_jira_backlog.py --check
```

Write every request body to `output/jira_backlog_preview.json` without calling JIRA. This
needs no credentials.

```bash
python src/create_jira_backlog.py --dry-run
```

Create one epic and its stories first, to check them in JIRA. `--epic` can be repeated.

```bash
python src/create_jira_backlog.py --epic 1
```

Then create everything:

```bash
python src/create_jira_backlog.py
```

Every created key is recorded in `output/jira_backlog_state.json`, so a re-run, or a resume
after a failure, skips what already exists and never makes duplicates. To re-create an
issue, delete its entry from that file.

New issues start in the project's default status, even though the epics document marks the
stories "Shipped". The tool doesn't change ticket status.

## 6. LLM image comparison (`src/build_llm_comparison.py`)

The viewer's image comparison scores each PDF/web image pair with a perceptual hash. This tool
gives a second opinion on the pairs the hash scores below 90%: a multimodal Gemini model, driven
through [DSPy](https://dspy.ai), says whether the two images show the same thing (IDENTICAL) or
not (DIFFERENT), with the differences it sees. Images are flattened, trimmed and scaled down,
batched several pairs per call, and judged concurrently within the provider's request and token
limits. Verdicts are cached, so a re-run costs nothing. It needs the built
`bcbc_pdf.json`, `bcbc_web.json` and `comparison.json` (§2–3 and the comparison build) in
`output/`.

### Configuration

The key and model come from the environment or a git-ignored `.env` in the project root, never
from a config file:

```
GEMINI_API_KEY=...
GEMINI_MODEL=...
```

Other settings (image size, batch size, rate limits, optional prices) are optional. Copy the
template to the git-ignored `llm_compare_config.toml`:

```bash
cp llm_compare_config.example.toml llm_compare_config.toml
```

`max_output_tokens` (default 8192) caps each call's output, thinking tokens included, which
Gemini-3-class models bill as output. `output_tokens_per_pair` (default 800) is the estimate
`--dry-run` and the token-per-minute reservation use; it is set from a measurement:
gemini-3.8-flash used 450-1,640 output tokens for a single pair and 3,374-5,967 for five. The
cap must cover `output_tokens_per_pair` x `max_pairs_per_call` plus room for the model's
thinking: too low truncates the answer, which then fails to parse and its pairs are re-asked
one at a time. Without a cap a looping answer would be billed in full on every re-ask; the
tokens of an answer that fails to parse are still counted in the report.

### Run

```bash
python src/build_llm_comparison.py --dry-run       # counts + estimated tokens/cost, no API call
python src/build_llm_comparison.py --limit 10      # try 10 pairs first
python src/build_llm_comparison.py --calibrate 24  # choose max_edge / batch size by evidence
python src/build_llm_comparison.py                 # the full run (resumable, cached)
```

`--dry-run` makes no API call and no network request (it makes litellm use its bundled price
map; set `LITELLM_LOCAL_MODEL_COST_MAP=False` to fetch the current one). `--calibrate N` judges
N sample pairs under several settings (this spends tokens) and prints the recommended
`max_edge` - put it in `llm_compare_config.toml` yourself. It also prints, per setting, the
estimated vs actual input tokens with the implied `token_scale`, and suggests the `token_scale`
to configure when the estimate is more than 15% off. When a setting judged fewer pairs than the
sample, a `<setting>: first error: ...` line gives its first error message (the API key
scrubbed, cut to ~200 characters), so a run where every call fails says why.

Rate limits (429), server errors (5xx), timeouts and dropped connections are retried with
exponential backoff; a provider's `retry_after` hint is honoured up to `retry_max_delay`.
Each request is cut off after `request_timeout_seconds` (default 120): the library's own wait
is 600 s, which once left a run hanging on one request for about 18 minutes, while single-pair
calls took 5-28 s in the 5-pair trial. A timed-out request is retried like any other, and the
provider may still bill the one that timed out. Other
errors (bad request, bad key, billing) fail that call's pairs as ERROR rows at once.

Exit codes: 0 success, 2 bad configuration or missing/malformed input, 130 interrupted with
Ctrl-C. Ctrl-C (pressed any number of times) stops the run within moments: verdicts already
given are kept with their tokens and cost and saved to the cache, pairs not yet judged show as
ERROR "run interrupted before this pair was judged", and the report is still written. A call
in flight when you press Ctrl-C may still be billed by the provider; its usage cannot be known.

### Results

Written to `--output-dir` (default: the same directory as `--source-dir`, i.e. `output/`):

- `llm_image_report.html` — every PDF and web image with its verdict, reasons, tokens and cost,
  and a header summary (this run's tokens and cost, and the cumulative tokens and cost of every
  LLM verdict shown, cached ones included); filter by verdict or search.
- `llm_image_compare.json` — the same data for programs.
- `llm_compare/cache.json` — the verdict cache; `llm_compare/calibration.json` after `--calibrate`.

From a git worktree (whose own `output/` and `.env` are empty), read the main checkout's
inputs and key with `--source-dir` and `--env-file`, and write somewhere else:

```bash
python src/build_llm_comparison.py --source-dir /path/to/PlayGround/output \
    --env-file /path/to/PlayGround/.env --output-dir /tmp/llm_out --dry-run
```

The report refers to images by a relative path back to `--source-dir`, so it opens correctly
from the output directory.

### Troubleshooting / what we measured

- Every call fails with `CERTIFICATE_VERIFY_FAILED` (`--calibrate` now prints it) on a python.org
  macOS Python: run that Python's `Install Certificates.command`, or run with
  `SSL_CERT_FILE="$(python3 -c 'import certifi; print(certifi.where())')"`.
- On gemini-3.8-flash, input tokens were billed flat per image (about 2,850 input tokens per pair
  whatever `max_edge` was), so scaling images down did not cut tokens: `max_edge` did not change
  token counts in the trial; it also bounds upload size. Output (thinking) tokens dominated the
  cost.
- Batching several pairs per call cut input by about 18% and output by about 40% in a 5-pair
  trial, but one verdict in five flipped (single-pair re-runs also flip occasionally). That is
  too few pairs to judge a larger `max_pairs_per_call`: calibrate with more before trusting it.

## Folder structure

- `app.py` — the FastAPI directory/Drive app; stays in the project root as its own entry
  point.
- `src/` — Python modules and scripts.
  - `mo_toc/` — the MO Package indexing library: `domain/` (pure dataclasses), `parsing/`
    (PyMuPDF adapter + tree/caption/image-matching rules), `output/` (JSON/Markdown/
    image writers), `web/` (FastAPI + static viewer assets).
  - `build_mo_toc.py` — CLI entry point that runs the mo_toc parsing pipeline.
  - `serve_mo_toc.py` — CLI entry point that serves the interactive web viewer.
  - `check_directory_access.py` — standalone CLI tool (see above).
  - `jira_backlog/` — the AOT Pulse JIRA backlog library: `parsing/` (epics document and
    spec.md readers), `domain/` (backlog records and the epic-to-spec mapping), `jira/`
    (REST client and issue fields), `output/` (Atlassian Document Format descriptions and the
    created-keys state file), `application/` (the publisher).
  - `create_jira_backlog.py` — CLI entry point that creates the backlog in JIRA (see §5).
  - `llm_compare/` — the LLM image comparison library: `domain/` (records, batching, costing),
    `parsing/` (pair source, image preprocessing), `analysis/` (DSPy judge, runner, rate
    limiter, estimate, calibration), `output/` (verdict cache, HTML/JSON report).
  - `build_llm_comparison.py` — CLI entry point for the LLM image comparison (see §6).
  - `shared/` — small pure-function helpers with no dependency on either indexing
    library, shared between `mo_toc/` and `web_toc/` (currently just the unified
    document-level numbering algorithm).
  - All scripts anchor their file paths (credentials, token, PDF, output) to the project
    root, not the current working directory, so they run correctly regardless of where
    they're invoked from.
- `tests/` — the automated test suite (1081 tests) for `src/mo_toc/`, `src/build_mo_toc.py`,
  `src/serve_mo_toc.py`, `src/web_toc/`, `src/build_web_toc.py`, `src/shared/`,
  `src/jira_backlog/`, `src/create_jira_backlog.py` and the other `build_*.py` scripts.
- `AOTPulse Specs/` — the AOT Pulse epics document and spec-kit specs read by §5 (ignored
  by git; kept locally).
- `data/` — input source files, e.g. `MO Package BCBC MRK signed.pdf`.
- `output/` — everything a program run produces (`bcbc_pdf.json`, `mo_toc.md`,
  `images/` for PDF images, `bcbc_web.json`, `web_images/` for cached web images).
  Regenerated by re-running the producing script; safe to delete and rebuild.
- `ai_docs/` — design notes and reports written during development, distinct from
  `output/`, which is only ever machine-generated by running a script.
- `Archive DO NOT Refer/` — retired code and its generated output from before the mo_toc
  rewrite (`bcbc_mo_index.py`, `bcbc2024_index.py`, `extract_figures.py`,
  `extract_figures_2024.py`). Not imported by anything active — kept for historical
  reference only.
- Root also holds `credentials.json` / `token.json` (OAuth secrets — never commit these),
  `jira_config.toml` (JIRA API token, ignored by git; template in `jira_config.example.toml`),
  `JIRA.postman_collection.json` (the JIRA API reference requests; it stores credentials,
  so it is ignored by git too), `.env` and `llm_compare_config.toml` (Gemini key/model and
  settings for §6, ignored by git; template in `llm_compare_config.example.toml`) and
  `requirements.txt`.
